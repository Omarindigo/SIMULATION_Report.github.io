1. Context

This documents an exploration into reinforcement learning for emergent locomotion. The original goal was a pipeline from custom 3D creature design (Blender) through physics simulation (PyBullet) and RL training (PPO) to a real-time Three.js viewer — a zoo of creatures that learned to move on their own, not through hand animation.

The project hit scalability limits with the original approach. PPO was too slow, the custom physics pipeline was fragile, and meaningful results required more data and faster iteration than the setup could deliver. The pivot to Gymnasium MuJoCo environments with SAC produced a working result: a Humanoid agent trained to 800K timesteps with clear gait progression.

This page records both phases — the original vision and the practical outcome — as an honest R&D log rather than a polished report.

2. Phase 1: Custom Creatures

2.1 The Pipeline

The original pipeline was designed as:

GLB body design (Blender) → physics simulation (PyBullet) → RL training (PPO / oscillator controllers) → trajectory export (JSON) → real-time viewer (Three.js)

Three creature types were implemented in creatures.py:

Bilateral Swimmer

8-segment chain with lateral undulation. Capsule segments connected by Z-axis revolute joints. Designed for snake/eel-like swimming motion using sinusoidal phase offsets.

Radial Starfish

Central sphere body with 5 arms arranged radially. Each arm is a capsule attached via a tangential revolute joint for pulsing motion. Asymmetric arm phasing creates directional movement.

Asymmetric Tumbler

Central body with 4 limbs at non-uniform angular offsets. Mixed Z-axis rotation with tangential components to produce chaotic tumbling rather than walking.

2.2 The Controller

An oscillator-based controller (controllers.py) drove each joint with sinusoidal position or velocity targets. Parameters like amplitude, frequency, phase stride, and bias could be tuned per-creature. This gave a crude approximation of locomotion without full RL — useful for early prototyping.

2.3 PPO Training Attempt

The initial RL approach used PPO via Stable-Baselines3 on these custom PyBullet environments. Training was slow. Each rollout required stepping through PyBullet physics on CPU, and PPO's on-policy updates discarded data after one pass. The result: marginal learning even after 250K timesteps, with slow iteration cycles that made debugging difficult.

A secondary path explored GLB-to-creature conversion via octo_from_glb.py and glb_topology.py, which inferred radial topology from 3D meshes — an attempt to bridge Blender design directly into simulation.

3. The Pivot

The original approach had three hard problems:

PPO was too slow

On-policy meant every gradient update consumed a full rollout. Sample efficiency was poor. With custom PyBullet environments running on CPU, a single training run to 250K timesteps took hours with marginal policy improvement.

PyBullet custom envs were fragile

Each custom creature required manual joint limit tuning, collision shape calibration, and reward function design. Debugging physics issues (penetration, instability, NaN velocities) consumed more time than training.

GPU underutilization

PPO's collect-once, update-once cycle couldn't keep an NVIDIA GPU saturated. Most of the training time was spent waiting for CPU-bound physics rollouts rather than GPU-accelerated gradient steps.

The decision was made to move off custom PyBullet creatures and onto Gymnasium's standard MuJoCo environments, and to switch from PPO to SAC for its off-policy efficiency and GPU-friendly training loop. This meant losing the custom creature zoo but gaining the ability to train at scale.

4. Phase 2: SAC Humanoid

With the pipeline moved to Gymnasium + MuJoCo + SAC, the training setup stabilised significantly. The Humanoid-v4 environment provided a 17-degree-of-freedom continuous control task with built-in physics, termination conditions, and reward structure — none of which needed to be written or debugged.

4.1 Reinforcement Learning Framework

The model is trained within a reinforcement learning setting in which an agent interacts with an environment over repeated cycles. At each timestep, the agent receives an observation, selects an action, receives a reward, and transitions to a new state. Stable-Baselines3 provides the implementation infrastructure; SAC provides the learning logic.

4.2 Soft Actor-Critic

SAC is an off-policy algorithm designed for continuous action spaces. It stores transitions in a replay buffer and reuses them across multiple gradient updates — this is the primary source of its sample efficiency advantage over PPO.

The SAC framework consists of three components:

  • Actor network — learns a stochastic policy mapping observations to action distributions.
  • Twin critic networks — estimate expected return while mitigating Q-value overestimation bias.
  • Target critic networks — stabilise learning via soft Polyak updates (τ = 0.005).

An entropy regularisation term keeps the policy exploratory during training. Rather than collapsing to deterministic behaviour early, the agent continues to sample from a distribution over actions. This is critical in high-dimensional continuous control where useful behaviour emerges gradually.

4.3 Training Loop

Each timestep follows: environment provides observation → actor selects action → environment steps → reward returned → transition stored in replay buffer. After enough transitions are collected, gradient updates begin. The critic is trained to minimise Bellman error against target values. The actor is trained to maximise expected return plus entropy. Target critics are soft-updated.

4.4 Implementation

The core training loop is in train_sac.py. Checkpoints are saved every 25K steps and later loaded by render_checkpoints.py which runs 1000 environment steps and writes a 1080p MP4. 69 checkpoints were saved across the 800K run.

model = SAC("MlpPolicy", env, verbose=1) model.learn(total_timesteps=400_000) model.save("sac_model")

5. Results

Four checkpoints were rendered at 1920 × 1080, 1000 frames each (~33 seconds at 30 fps). The progression shows a clear trajectory from uncoordinated joint movement to stable walking.

6. Key Learnings

Off-policy > on-policy for GPU-accelerated continuous control

SAC's replay buffer made effective use of GPU parallelism. PPO spent most of its time collecting rollouts on CPU. For this hardware setup, the switch was worth roughly 3-4x in effective throughput.

Pre-built environments accelerate iteration

Custom PyBullet creatures required constant debugging of physics parameters, collision geometry, and reward shaping. Gymnasium MuJoCo environments removed an entire class of failure modes from the critical path.

800K timesteps is a starting point, not an endpoint

The agent walks at 800K but still shows room for improvement — occasional stumbles, inefficient energy use, and sensitivity to terrain variation. Longer training (2M+ timesteps) would likely produce more robust behaviour.

The custom creature questions remain open

The original vision of a Three.js creature zoo was deprioritised but not invalidated. The SAC training pipeline now exists as a reliable foundation. Revisiting custom MuJoCo XML creatures with SAC training is the natural next step.

7. Next Steps

  • Revisit custom MuJoCo XML creatures (swimmer, starfish, tumbler) using the SAC training pipeline instead of PPO
  • Build a Three.js or WebGL viewer that loads exported trajectory JSON from any trained creature
  • Train to 2M+ timesteps to push gait quality further
  • Explore reward shaping for specific movement aesthetics (smoothness, symmetry, energy efficiency)
